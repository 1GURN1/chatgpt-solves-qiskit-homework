## Abstract

This project investigated whether Qiskit homework assignments for an undergraduate quantum computing course can be redesigned to be more resistant to direct completion by generative AI tools. The original goal was to build AI-resilient, auto-gradable assignments using seeded circuit generation, simulator execution, noisy simulation, machine-readable JSON outputs, QPY circuit validation, hidden reference generation, and optional IBM Quantum hardware execution. Over the course of the project, the main finding became a negative result: ordinary Qiskit assignments, and even some assignments with common AI-deterrence modifications, can often still be completed effectively by a minimally engaged student using ChatGPT. This report summarizes the experiments, negative results, hardware findings, assignment prototypes, and design principles that emerged from the project.

## 1. Introduction

Generative AI tools such as ChatGPT and ClaudeAI can solve many conventional programming and conceptual homework tasks when students provide the assignment text or files. This creates a challenge for courses in quantum software development, where assignments often ask students to implement standard algorithms such as Quantum Phase Estimation, Quantum Fourier Transform, Deutsch-Jozsa, and Grover’s Algorithm using Qiskit.

This directed research project began with the goal of developing AI-resilient and autogradable Qiskit homework assignments. The original idea was to create assignments where the final graded answer depends on actual execution rather than only written explanation. Proposed techniques included seeded generation, simulator outputs, noisy simulation, IBM hardware results, transpiler statistics, JSON submission files, QPY circuit validation, and hidden instructor reference functions.

As the project progressed, the focus shifted toward documenting a clear negative result. Ordinary Qiskit homework assignments, and even assignments with basic AI-deterrence methods, remained vulnerable to completion by a “lazy student plus ChatGPT” workflow. This does not mean ChatGPT is always correct or that all protections are useless. Rather, it shows that simple protections do not reliably ensure student understanding.

## 2. Research Questions

The project was organized around the following research questions:

1. Which Qiskit homework tasks are most suitable for AI-resilient, auto-gradable assessment?
2. Can seeded, execution-dependent Qiskit assignments be made reliable and accessible in Google Colab?
3. Can an autograder verify circuit artifacts, expectation values, noisy-simulation summaries, and transpiler statistics with useful feedback?
4. How well do text-only LLM attempts perform when asked to solve these assignments without running Qiskit?
5. What design principles emerge for balancing accessibility, AI-resilience, grading reliability, and conceptual learning?

The work most strongly addressed RQ4, because many experiments directly tested how well ChatGPT could complete standard Qiskit tasks. The work also addressed RQ1, RQ2, RQ3, and RQ5 through the construction of HW1-HW3 assignment prototypes and associated reference/grading utilities.

## 3. Threat Model

The practical threat model is a disengaged or minimally engaged student who uses ChatGPT to complete a homework assignment. The workflow is:

1. Paste the homework text or notebook instructions into ChatGPT.
2. Ask for complete Qiskit code or a filled notebook.
3. Run the generated code in Colab or Jupyter.
4. Ask ChatGPT to debug import errors or runtime errors.
5. Copy generated explanations or reflection answers.
6. Submit outputs without a strong understanding of the quantum algorithm.

This threat model is realistic because it does not assume a sophisticated attacker. It assumes a student who wants to complete the assignment quickly with minimal learning.

## 4. Baseline Experiments

### 4.1 Quantum Phase Estimation

Quantum Phase Estimation was one of the first major experiments. ChatGPT was asked to produce Qiskit code for simulator execution and IBM hardware execution. The result was that ChatGPT could produce working or near-working code. The simulator result matched the expected dominant bitstring and phase calculation. The IBM hardware result was noisy but still had the expected bitstring as dominant.

This showed that small QPE assignments are vulnerable to ChatGPT assistance. The student may need to install missing packages or provide an IBM API token, but the main code and explanation can be generated by the model.

### 4.2 Quantum Fourier Transform

The QFT experiment used a QFT followed by inverse QFT recovery circuit. A known input bitstring was prepared, QFT was applied, inverse QFT was applied, and the circuit was measured. The simulator produced the expected output `101` for all shots in the tested version.

The IBM hardware run on `ibm_kingston` also produced `101` as the dominant output, with 3709 out of 4096 shots, or about 90.55%. Other bitstrings appeared because of hardware noise. The circuit depth also increased after transpilation, from 10 to 32, showing how backend execution changes the concrete circuit.

The QFT experiment showed that hardware adds useful evidence and noise interpretation, but it did not prevent ChatGPT from writing useful code.

### 4.3 Deutsch-Jozsa

Deutsch-Jozsa was explored both as a standard algorithm and as a seeded assignment. A standard Deutsch-Jozsa task is easy for ChatGPT to solve because the circuit structure is widely known. The more useful design was a seeded Deutsch-Jozsa assignment where each student receives a custom oracle mask.

The custom mask determines which input qubits control the output qubit. Students must classify the oracle as constant or balanced before building it. This improves the assignment because a generic Deutsch-Jozsa solution is no longer enough; the student must use their specific seed-generated oracle configuration.

### 4.4 Grover’s Algorithm

Grover’s Algorithm was discussed as a planned stronger assignment. A simple Grover example is still within ChatGPT’s capabilities. However, Grover becomes more useful for AI-resilient design when it uses a seeded marked state, custom oracle construction, non-palindromic bitstrings, scaling, and hardware/noise interpretation.

## 5. Negative Results

The project produced several negative results.

First, standard Qiskit homework is often solvable by ChatGPT. ChatGPT can usually generate Qiskit code for common algorithms such as QPE, QFT, Deutsch-Jozsa, and Grover. It can also provide plausible explanations.

Second, basic “do not use AI” instructions are not technically effective. They clarify policy but do not prevent a student from asking ChatGPT for help.

Third, hidden text, canary markers, and altered output labels have limited value. They may reveal careless AI use, but students can remove suspicious phrases or regenerate answers.

Fourth, altered wording does not meaningfully stop ChatGPT if the underlying task remains a recognizable standard algorithm.

Fifth, simulator-only execution is not enough if the task is generic. ChatGPT can write simulator code and often predict deterministic results.

Sixth, IBM hardware execution helps but does not fully solve the problem. Hardware adds queue delays, backend names, job IDs, transpilation, and noise, but ChatGPT can still generate the code and expected theoretical interpretation.

Seventh, too much scaffolding can accidentally give away the answer. If the student notebook includes the full expected-output function, the student does not need to reason through the assignment. The answer-generation logic should remain in instructor/reference files.

Finally, generic reflection questions are weak because ChatGPT can answer them. Reflections become stronger when they require students to discuss their own counts, backend, dominant bitstring, circuit depth, and result classification.

## 6. Hardware-Based Findings

Hardware execution is useful because it introduces real execution artifacts that are difficult to know before running the job. These include backend name, job ID, raw counts, queue/runtime behavior, transpiled depth, and noise distribution.

However, hardware is not a complete solution. ChatGPT can write IBM Runtime code, explain expected results, and guide result interpretation. In the QPE and QFT experiments, hardware results were noisy but still interpretable. The correct expected result remained dominant.

The best use of hardware is as an optional or structured extension to the reliable simulator-based core. Hardware should be used to support discussion of noise, transpilation, and real-device limitations, not as the only exact autograded output.

## 7. Assignment Prototypes Built

### 7.1 HW1: Seeded Circuits, Bit Flips, and Measurement Mapping

HW1 introduces the core assignment infrastructure. Each student receives a seeded configuration including an initial bit pattern, bit-flip mask, and measurement map. Students build the circuit, run the simulator, interpret the displayed bitstring, and export `answers.json`.

The main resilience layer is Qiskit bit ordering. Qiskit displays counts as `c[n-1]...c[0]`, which may differ from the way students list qubits. Non-symmetric bitstrings and custom measurement maps expose common mistakes.

### 7.2 HW2: QFT / Inverse QFT Hardware Recovery

HW2 extends the structure into a quantum algorithm. Students prepare a seeded input, apply QFT, apply inverse QFT, and measure. The simulator should recover the original bitstring. Students also record circuit metrics and optionally run a smaller version on IBM hardware.

This assignment uses seeded bitstrings, measurement maps, circuit depth, operation counts, and optional hardware evidence.

### 7.3 HW3: Seeded Deutsch-Jozsa

HW3 uses a seeded oracle mask. Students classify the oracle before building it, implement the oracle, run Deutsch-Jozsa, and interpret the simulator result. The mask determines which input qubits control the output qubit. A nonzero mask creates a balanced oracle, while an all-zero mask creates a constant oracle.

This assignment is stronger than a generic Deutsch-Jozsa task because the student must build a custom oracle from their seed.

## 8. Hidden Reference Generation and Autograding

A major part of the assignment design is hidden reference generation. Instead of manually storing every student’s answer, the instructor uses deterministic functions to regenerate the correct assignment instance and expected answer from the student ID.

The common reference functions include:

- `generate_config(student_id)`: creates the personalized assignment instance.
- `reference_answers(student_id)`: computes the instructor-side expected answer.
- `validate_answers(student_answers, student_id)`: compares submitted JSON to the hidden reference.
- `schema_hwX.json`: checks that required fields and types are present.
- `grader_hwX_demo.py`: demonstrates simple autograding.

This makes assignments personalized but still gradeable.

## 9. LLM Boundaries and Failure Points

ChatGPT does not have a simple fixed qubit limit for writing code. It can generate circuits for many qubits, but that does not mean the circuits are practical or the results are meaningful.

Observed LLM boundaries include:

- inability to know actual hardware results before execution
- bit-ordering confusion
- custom oracle mistakes
- outdated Qiskit or IBM Runtime syntax
- missing optional libraries such as `pylatexenc`
- overconfident interpretation of noisy histograms
- difficulty proving that a circuit exactly matches the intended algorithm

These failure points can be used constructively in assignment design.

## 10. Proposed Remaining Assignments

### HW4: Grover Search with Custom Marked State

Students receive a seeded marked state, build the oracle and diffuser, run simulator, optionally run hardware, and scale the number of qubits until results become noisy or inconclusive.

### HW5: Circuit Repair + Transpiler Fingerprint

Students receive a broken seeded circuit, repair it, submit `answers.json` and optionally `circuit.qpy`, and report original/transpiled depth, operation counts, two-qubit gate counts, and layout/routing information.

## 11. Design Principles

The project suggests the following design principles:

1. Use seeded personalization so each student receives a unique but reproducible task.
2. Require machine-readable outputs such as `answers.json` for autograding.
3. Keep full answer-generation logic in instructor/reference files, not in student notebooks.
4. Use non-symmetric bitstrings and custom measurement maps to expose bit-ordering mistakes.
5. Require actual simulator execution rather than only written explanations.
6. Use hardware execution as an optional or structured evidence layer, not the sole graded output.
7. Tie reflection questions to the student’s own generated results.
8. Collect circuit artifacts such as QPY files when deeper validation is needed.
9. Add short in-class quizzes or oral checks to verify conceptual understanding.

## 12. Conclusion

The project’s main finding is that ordinary Qiskit homework assignments are not AI-resilient. Even common protection methods such as hidden text, canary markers, altered wording, or generic reflection questions do not reliably stop a minimally engaged student from completing the assignment with ChatGPT.

The constructive result is that assignments can be redesigned to require personalized execution, machine-readable artifacts, hidden reference checking, simulator/hardware comparison, and conceptual explanation tied to actual results. This does not make AI use impossible, but it shifts the assessment toward evidence of execution and understanding rather than generic answers.

The final assignment package should therefore focus less on preventing AI use directly and more on requiring students to run, verify, interpret, and defend their own quantum computing results.
